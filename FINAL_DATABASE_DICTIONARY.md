## Known Limitations Discovered During Stress-Testing

1. **Compression vs RLS incompatibility (TimescaleDB 2.29.1):** `ALTER TABLE ... SET (timescaledb.compress)` cannot coexist with `ENABLE ROW LEVEL SECURITY` on the same hypertable, in either order. Error observed: `columnstore cannot be used on table with row security`. Since per-tenant RLS is a hard security requirement, compression was **dropped** for `system_metrics` and `zabbix_history_cache`; retention policies (which ARE compatible with RLS) were kept. This differs from earlier design assumptions and from what production migrations intended (production never actually validated this because the TimescaleDB extension is not installed there).
2. **Fail-closed on missing tenant context:** if `app.current_tenant_id` is not set before querying a RLS-protected table, the query raises `invalid input syntax for type uuid: ""` rather than returning zero rows silently. This is a _safe_ failure mode (no data leak) but means the API layer MUST always set the tenant context (via `SET LOCAL` / `AsyncLocalStorage`, exactly as `@repo/db` already does) before running ANY query against a tenant-scoped table, including tables with nullable `tenant_id` (global feature flags, etc.) — otherwise even legitimate "global" reads will error out.
3. **`onboard_tenant_schema` clones structure only:** RLS policies, indexes, and constraints from `tenant_template` tables ARE copied (`LIKE ... INCLUDING ALL`), but ownership/grants may need to be re-applied per tenant schema in a production rollout script.
